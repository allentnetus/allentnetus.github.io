## 一、文档定位

这套方法的定位是：

> 面向单人或小团队、单个代码仓库、需求相对明确、风险中低的软件项目的 AI Agent 辅助研发执行 SOP。

它主要解决的是 Agent 协作中的任务拆分、会话管理、职责边界、依赖协同、测试审查和人工验收问题；它不是完整的组织级项目管理体系，也不能替代产品路线图、资源管理、预算管理、合规治理和跨团队协调。

本文为整合后的完整版，在原版基础上补充了运行环境冲突管理、权限落地配置、证据防伪造、Token 成本控制、人工验收清单和分层采用方案六个部分。完整流程不必一次到位：第二十一节给出轻量版 / 标准版 / 完整版三档采用方案，个人项目和小任务可以从轻量版起步，随耦合程度、并行需求和风险等级上升再逐步升级。

## 二、适用范围

### 2.1 最适合

- Web、App、小程序和桌面工具
- CRUD、后台管理系统和内部业务工具
- 个人项目和小型团队项目
- 从原型到 MVP 的软件开发
- 单个代码仓库、需求相对明确的项目
- 可以通过接口、Mock 或中间产物拆分的模块化项目
- 测试能够验证真实行为的项目

这类项目通常能够回答：

1. 每个目标的产物是什么？
2. 谁负责执行？
3. 如何验证完成？
4. 哪些操作必须人工批准？
5. 目标之间的依赖在哪里？

### 2.2 可以使用，但需要扩展

- 多模块平台
- 前后端分离项目
- 有较多外部接口的系统
- 中等规模团队协作
- 数据处理和自动化工作流

建议增加：

- 任务依赖图
- API、数据和版本契约
- 集成任务和联调阶段
- 风险登记册
- 变更审批
- 发布、回滚和环境管理

### 2.3 不适合直接套用

#### 需求高度不确定的探索项目

新产品验证、算法探索和研究型项目应增加：

```text
假设 → 实验 → 结果 → 决策
```

不应一开始就固定完整的“总控—开发—测试—审查”流水线。

#### 高度耦合的大型系统

如果多个目标频繁修改同一批文件、共享大量状态，应使用父目标、子系统边界和集成会话，不要强行执行“一目标一会话”。

#### 生产运维和持续运营

线上故障、持续交付和日常运营更适合 Kanban、事件响应、变更管理和服务级别管理，而不是一次性顺序流程。

#### 高风险或强监管项目

支付、医疗、金融、真实用户数据和生产部署项目，还必须增加：

- 权限分级
- 审批记录
- 安全审计
- 数据脱敏
- 回滚演练
- 发布门禁
- 责任人和合规记录

#### 多团队、跨组织项目

这套方法只能管理 Agent 辅助研发执行，不能替代：

- 产品路线图
- 预算和资源分配
- 团队容量管理
- 外部供应商协调
- 组织级优先级
- 跨团队承诺和升级机制

## 四、核心原则

### 4.1 项目和会话的基本关系

> 一个项目 = 一个事实源 + 多个目标会话（不同角色）；每个会话只负责自己的工作，避免上下文过长、节省 Token。

> 并行写代码使用独立 Worktree；重要操作需要人工验收。

这里的“一个目标一个会话”不是要求目标之间完全没有依赖，而是要求每个会话具备清楚的：

- 责任边界
- 输入和依赖
- 输出产物
- 验收标准
- 变更入口
- 交接记录

因此：

> 独立执行 ≠ 没有依赖；独立执行 = 责任、产物和验收边界清晰，依赖关系显式可追踪。

### 4.2 Agent 的职责边界

- 总控负责目标、范围、计划、依赖和证据汇总。
- 执行会话负责形成代码、设计或其他明确产物。
- 测试会话负责验证真实行为和最终状态。
- 审查会话负责发现需求、质量、安全和可维护性问题。
- 人负责高风险操作和最终验收决定。

Agent 可以分析、规划、执行和报告，但不能因为遇到新情况而擅自扩大任务范围、修改其他目标的成果、修改真实数据或部署正式环境。

### 4.3 过程必须留下证据

每个任务完成后必须提供可检查的证据，例如：

- 改动文件和 Git diff
- 启动或构建结果
- 测试命令和测试报告
- 截图、日志和复现步骤
- 审查问题清单
- 人工验收结论
- 状态、决策和交接记录

不能只以“已经完成”作为完成依据。

## 五、项目初始化：建立事实源

建议在本地指定文件夹下建立长期项目，不把 AI Agent 会话临时目录作为项目正式目录。

一个适合这套方法的最小结构如下：

```text
项目名称/
├─ AGENTS.md                         # 项目规则、命令、边界和验收要求
├─ 01_项目资料/
│  ├─ 产品需求.md
│  ├─ 开发计划.md
│  └─ 总控规则.md
├─ 02_代码/                          # 实际代码
├─ 03_测试记录/                      # 测试报告、问题记录
├─ docs/
│  ├─ status.md                      # 当前状态、阻塞项、下一步
│  └─ decisions/                     # 已确认的产品和技术决策
├─ tasks/                            # 一个目标一条任务记录
├─ tests/                            # 测试代码、测试用例和测试脚本
├─ evidence/                         # 截图、日志、验收清单和证据
└─ .gitignore
```

目录职责应保持分离：

- `01_项目资料/` 保存需求、计划和总控规则，原始资料必须可追溯。
- `02_代码/` 保存实际代码，开发会话主要在此范围内工作。
- `03_测试记录/` 保存测试报告和问题记录，不与测试代码混在一起。
- `docs/status.md` 保存项目当前状态，不依赖聊天记忆。
- `docs/decisions/` 保存已确认的决策、变更原因和适用范围。
- `tasks/` 保存任务契约、依赖关系和任务状态。
- `tests/` 保存自动化测试、测试用例和验证脚本。
- `evidence/` 保存截图、日志、命令输出和验收证据。

`AGENTS.md` 至少应写清楚：

- 项目目标和当前阶段
- 技术栈、安装、启动、测试和构建命令
- 目录职责和允许/禁止修改的范围
- 真实数据、测试数据和生产环境边界
- Git、分支和 Worktree 约定
- 完成定义和验收标准
- 出现阻塞、冲突或不确定要求时的处理方式

## 六、总控/需求会话：定义任务契约

总控会话的主要职责是：

- 分析需求和当前项目状态
- 明确目标、范围和优先级
- 识别任务之间的依赖和共享资源
- 拆分可执行任务
- 制定开发、测试、审查和验收计划
- 明确任务完成需要提交哪些证据
- 汇总执行结果并更新项目状态

总控会话不应代替执行会话：

- 不直接编写业务代码
- 不作为测试执行会话
- 不作为审查执行会话
- 不擅自修改其他会话的产物
- 不擅自扩大目标范围

但总控可以读取和检查执行结果，例如查看 Git diff、测试报告、审查报告和证据文件，以确认交接是否完整；这不等于总控代替测试或审查。

每项任务开始前，建议形成如下任务契约：

```text
任务编号：TASK-001
任务目标：要解决的具体问题或要形成的结果
输入与依据：需求文件、接口契约、现有代码、设计稿
依赖任务：depends_on
阻塞任务：blocks
共享接口/数据：shared_contract、shared_data
允许修改：明确的目录或文件
禁止修改：明确的目录、数据和环境
输出产物：代码、设计稿、报告、文档或其他文件
验收标准：可验证、可量化的完成条件
风险与限制：数据、权限、兼容性和部署风险
下一位负责人：开发、UI、测试、审查或人工验收
```

任务完成时必须回报：

- 做了什么
- 修改了哪些文件
- 使用了什么命令或工具
- 验证是否通过
- 证据保存在哪里
- 遗留问题、风险和下一步是什么

## 七、会话管理：按独立结果拆分

### 7.1 推荐的会话边界

会话最好按“独立结果”划分，而不是机械地按角色长期建立永久会话。例如：

```text
项目-需求澄清与任务拆分
项目-首页功能实现
项目-登录问题修复
项目-接口联调
项目-版本验收
```

可以在会话中使用开发、UI、测试和审查等角色提示，但会话边界应优先由目标和产物决定。

### 7.2 什么时候保持同一会话

下列情况应继续使用同一个会话：

- 任务仍属于同一个最终结果
- 正在连续执行多个步骤
- 中间状态对下一步非常重要
- 频繁切换会造成明显的背景丢失
- 尚未完成验收闭环

### 7.3 什么时候新建会话

下列情况适合新建会话：

- 目标结果已经变化
- 需要独立审查或独立验证
- 任务可以并行执行
- 当前会话上下文已经过长
- 需要隔离不同的权限、分支或 Worktree
- 需要把一个问题作为独立 Bug 或集成任务跟踪

重要背景、决策和交接不能只留在聊天记录中，应写入 `AGENTS.md`、`docs/status.md`、`docs/decisions/`、`tasks/` 或 `evidence/`。

## 八、不同角色的责任和产物

### 8.1 开发会话

职责：

- 只负责代码实现和必要的自动化测试
- 主要修改 `02_代码/`
- 不修改 `01_项目资料/` 和 `03_测试记录/` 中的正式资料，除非任务契约明确允许
- 遵循最小修改原则
- 完成后提供运行和测试说明

产物：

- 代码改动
- 单元测试或测试更新
- Git diff 或提交记录
- 运行说明
- 已知限制和交接说明

开发完成报告至少应说明：应用是否能够正常运行、修改了哪些代码、测试如何执行、还有哪些未完成事项。

### 8.2 UI 会话

职责：

- 负责界面结构、视觉设计、交互设计和使用说明
- 可以修改明确授权的 UI 或视觉文件
- 不擅自修改业务逻辑、接口契约和数据模型

产物：

- 设计稿或界面截图
- 组件和交互说明
- 使用说明
- 与开发会话的接口或资源交接说明

### 8.3 测试会话

职责：

- 只负责测试和问题复现
- 不直接修改业务代码
- 在隔离的测试数据和测试环境中验证真实行为

至少覆盖：

1. 安装、启动和基本运行
2. 核心功能
3. 异常输入和异常流程
4. 文件、数据库或其他最终状态
5. 关键接口和边界条件

产物：

- 测试报告
- 通过/失败清单
- 截图、日志或命令输出
- 可复现的问题单
- 复现步骤、预期结果和实际结果

发现问题时，测试会话把问题交给开发会话修复；开发修复后重新回到测试会话进行回归验证。

### 8.4 审查会话

职责：

- 对业务代码只读，不直接修改被审查的业务代码
- 可以新增审查报告、问题清单和审查证据，但不得覆盖原始测试证据
- 核对需求符合性
- 检查代码质量、可维护性和安全风险
- 检查 diff、测试证据、文档和回滚方案

产物：

- 审查报告
- 问题清单
- 问题等级和影响范围
- 修复建议
- 是否建议进入人工验收的结论

审查发现问题时，由开发会话修复；审查会话不应直接越过责任边界改代码。

### 8.5 人工验收

人工负责最终判断：

- 结果是否符合真正的业务意图
- 是否接受已知限制和剩余风险
- 是否允许发布、部署或修改真实数据
- 是否需要退回开发、测试或审查环节

Agent 可以汇总结果和提出建议，但不替人作高风险最终决定。验收的具体操作清单、冒烟用例和结论表单见第十八节。

## 九、标准工作流程

推荐主流程为：

```text
需求契约
   ↓
依赖识别
   ↓
开发 / UI
   ↓
测试
   ↓
审查
   ↓
人工验收
   ↓
更新 status、decision、evidence
```

如果任务没有依赖，可以在“开发 / UI”阶段并行推进；如果有依赖，则应先完成前置任务或先冻结共享契约。

更完整的分叉流程如下：

```text
                         ┌─ 目标 A：开发 ─┐
需求契约 → 依赖识别 ────┤                ├→ 集成任务 → 联调回归
                         └─ 目标 B：UI/API ┘              ↓
                                                   审查
                                                     ↓
                                                   人工验收
                                                     ↓
                                               更新项目状态
```

底层闭环可以概括为：

```text
需求契约 → 开发/UI → 测试 → 审查 → 人工验收 → 更新状态
                         ↑       │
                         └─ 修复 ┘
```

## 十、目标之间产生耦合时的管理方式

### 10.1 不要强行维持“完全独立”

目标在推进过程中出现耦合是正常的。风险不在于存在依赖，而在于依赖没有被识别、记录和管理。

应将目标关系记录为：

```text
当前任务：TASK-002
depends_on：TASK-001
blocks：TASK-004
shared_contract：登录接口 v1
shared_data：用户会话结构
integration_owner：总控或指定集成会话
状态：待开始 / 执行中 / 等待 / 阻塞 / 集成 / 待验收 / 已完成
```

### 10.2 先定义最小共享契约

例如 UI 和 API 存在依赖时，先定义：

```text
接口名称：登录接口
输入：用户名、密码
输出：会话信息或错误信息
错误格式：统一错误码和提示字段
验收标准：成功、失败、空输入和异常网络场景
变更方式：先更新契约和 decision，再修改实现
```

在契约稳定前，可以使用 Mock、测试桩或示例数据让双方继续推进，减少不必要的等待。

### 10.3 增加明确的集成任务

当目标需要联调时，不要让各个会话临时互相修改范围，而应建立独立的集成任务，例如：

```text
TASK-INT-001：前后端接口联调
TASK-INT-002：数据库迁移验证
TASK-INT-003：跨模块回归测试
TASK-INT-004：发布前配置和环境验证
```

集成任务负责处理共享接口、共享数据、冲突、联调和跨目标回归。

### 10.4 何时保持分开，何时合并

可以继续分开的情况：

- 可以通过接口、Mock 或中间产物隔离
- 各自可以形成可验收的中间结果
- 不需要频繁修改同一批文件
- 验收标准可以分别定义

应合并为父目标或联合会话的情况：

- 频繁往返同步，交接成本已经高于拆分收益
- 经常修改同一批文件
- 共享同一套不可拆分的验收标准
- 一个目标没有另一个目标就无法形成有意义的产物

不要为了“节省 Token”而强行把高度耦合的工作拆散；过度拆分会增加交接、冲突和重复分析成本。

### 10.5 发现耦合后的处理步骤

```text
发现新依赖
   ↓
暂停可能受影响的修改
   ↓
标记 Waiting 或 Blocked
   ↓
更新依赖表、任务契约和 decision
   ↓
选择：补充契约 / 新增集成任务 / 调整顺序 / 合并会话
   ↓
继续执行并保留 evidence
```

发现耦合不是失败；未识别、未记录、未授权地处理耦合才是风险。

## 十一、顺序、并行、Worktree 和交接规则

### 11.1 顺序执行

适用于：

- 有明确前置任务
- 共享接口尚未确定
- 数据迁移必须先完成
- 后一步必须依赖前一步的真实结果

### 11.2 并行执行

只并行真正独立的任务，例如：

- UI 设计和后端接口调研
- 不同模块且不共享文件的实现
- 测试用例准备和文档整理
- 只读代码探索和日志分析

### 11.3 Worktree 隔离

并行写代码时使用独立分支或独立 Worktree，避免多个会话直接修改同一工作区。

需要遵守：

- 多个会话不得同时修改同一批文件
- 每个 Worktree 对应清楚的任务和分支
- 集成前先检查 diff、依赖和测试结果
- 集成后删除或归档不再需要的临时 Worktree
- 不把未提交的真实数据、密钥和本地状态误带入并行环境

> Worktree 只解决文件级冲突；端口、数据库、构建缓存等运行环境冲突的管理见第十二节。

### 11.4 交接要求

交接时必须更新：

- `docs/status.md`
- `docs/decisions/` 中相关决策
- `tasks/` 中任务状态和依赖
- `evidence/` 中测试、审查和验收证据

交接记录至少说明：当前状态、完成内容、未完成内容、依赖、阻塞、证据路径和下一位负责人。任务完成后应归档会话和交接记录。

## 十二、运行环境冲突管理

### 12.1 Worktree 解决不了环境冲突

Worktree 隔离的是同一代码库中的文件改动，不能隔离运行环境。并行会话仍然共享端口、数据库、依赖、缓存、环境变量和外部资源，冲突随时可能发生：

- 多个会话同时启动开发服务器或测试服务，抢占同一端口
- 数据库迁移互相冲突，测试数据互相覆盖
- node_modules、构建缓存、编译产物被并发重建或互相污染
- 环境变量、代理和凭据指向同一套服务，行为互相干扰
- 消息队列、云存储、第三方 API、部署环境等外部资源互相踩踏

### 12.2 常见冲突与对策

| 冲突类型 | 典型表现 | 对策 |
| --- | --- | --- |
| 端口占用 | 第二个 dev server 启动失败或行为异常 | 任务契约中分配固定端口段（如 3000-3010），测试服务用独立端口 |
| 数据库 | 迁移互相冲突、测试数据污染 | 每个 Worktree 使用独立 schema 或独立测试库；迁移只在集成任务中统一执行 |
| 构建缓存 | 并行构建互相踩缓存，产物不一致 | 并行会话不共享 build 目录；集成前统一重新构建 |
| 依赖安装 | node_modules 被并发改写 | 依赖安装串行化，或各 Worktree 独立安装并锁定版本 |
| 环境变量 | 配置互相覆盖，行为漂移 | 通过独立 .env 文件或环境变量注入区分环境 |
| 外部资源 | 队列、存储、API 调用互相干扰 | 登记占用者；写操作串行化；使用独立测试账号或沙箱 |

### 12.3 环境分配表

并行开始前，总控在任务契约中声明 `shared_environment`，并在任务表中登记每个会话的环境分配：

```text
TASK-002 环境：端口 3001 / 数据库 test_db_b / 缓存目录 .cache-002 / 环境变量文件 .env.task-002
TASK-003 环境：端口 3002 / 数据库 test_db_c / 缓存目录 .cache-003 / 环境变量文件 .env.task-003
```

### 12.4 冲突处理步骤

```text
发现运行冲突
   ↓
暂停可能受影响的会话
   ↓
标记 Waiting 或 Blocked
   ↓
重新分配端口 / 数据库 / 缓存，或改为串行执行
   ↓
记录冲突原因和处理结果到 evidence
   ↓
继续执行
```

## 十三、风险和权限边界

必须在项目规则和每项任务中重复强调：

- 任何角色不得超出任务范围
- 总控不替执行会话做事
- 测试和审查默认不修改业务代码
- 开发不得擅自修改正式需求、测试结论或真实数据
- 未经许可不得修改真实数据
- 未经许可不得部署正式环境
- 高风险操作必须人工批准
- 发布前要有回滚方案
- 测试数据和生产数据必须隔离
- 不能只靠提示词宣称“禁止修改”，还要使用 Git、Worktree、环境隔离、检查和审批形成实际控制

提示词中的“允许修改/禁止修改”是行为约束，不等同于系统权限。对于真实数据、支付、生产部署、外部发送和不可逆变更，应增加真正的权限控制和人工门禁，具体落地配置见第十四节。

## 十四、权限控制的落地配置

### 14.1 原则

> 提示词中的“允许修改/禁止修改”是行为约束，不等同于系统权限。

仅靠提示词约束真实数据、支付、生产部署和不可逆变更是不够的，还必须通过平台机制形成实际控制。AI Agent 及同类平台通常提供以下能力：

| 机制 | 作用 | 推荐配置 |
| --- | --- | --- |
| 审批模式（Approval modes） | 控制 Agent 能否自动执行操作 | 默认“建议更改”或按需批准；只读探索用只读模式 |
| 命令允许/拒绝列表 | 白名单放行安全命令，拦截危险命令 | 部署、删除、数据库写操作默认拦截 |
| 文件访问范围 | 限制 Agent 可读写的目录 | 开发会话仅放开 `02_代码/` 和对应测试目录 |
| 环境变量隔离 | 生产凭据不进开发环境 | 生产密钥只存在于受控环境，不写入代码和文档 |
| Git 分支保护 | 防止直接推送到受保护分支 | main 禁止直接推送，变更走 PR 或合并请求 |
| 部署门禁 | 生产发布必须人工触发 | 部署由人在 CI/CD 或运维平台手动触发 |
| 审计日志 | 记录 Agent 执行过的命令和变更 | 关键操作日志归档到 evidence |

### 14.2 按角色的最小权限建议

| 角色 | 可写范围 | 必须人工批准的操作 |
| --- | --- | --- |
| 总控 | docs/、tasks/、evidence/ | 修改需求基线、扩大目标范围 |
| 开发 | 02_代码/、对应 tests/ | 修改真实数据、部署、删除数据、变更接口契约 |
| UI | 明确授权的 UI/视觉文件 | 修改业务逻辑、接口契约和数据模型 |
| 测试 | 03_测试记录/、evidence/、独立测试环境 | 修改业务代码、写生产数据 |
| 审查 | 对业务代码只读；可新增审查报告、问题清单和审查证据 | 不得修改业务代码或覆盖原始测试证据 |

### 14.3 高风险操作清单

以下操作默认需要人工批准，并配置为“需要确认”的级别：

- 修改、删除或覆盖真实数据
- 执行数据库迁移或 DDL
- 部署或切换生产环境
- 发送外部消息、邮件或执行资金操作
- 不可逆的批量操作（批量删除、覆盖文件、回滚）
- 修改权限、凭据或安全配置

每次批准都应留下记录（谁、什么操作、何时、批准依据），归档到 `evidence/`，作为审计和追溯依据。

## 十五、证据和完成定义

一个任务只有同时满足以下条件，才建议标记为完成：

1. 目标结果已经形成。
2. 实际修改范围与任务契约一致。
3. 测试验证了真实行为，而不只是命令退出码。
4. 文件、数据库或外部系统的最终状态符合预期。
5. 测试、审查和交接证据已经保存。
6. 已知问题、限制和风险已经明确记录。
7. 高风险操作已经获得人工批准。
8. `status`、`decision` 和 `evidence` 已更新。

> 证据的可复核性与防伪造机制见第十六节。

### 15.1 风险判断维度

风险等级不按项目规模简单判断，而应至少从以下四个维度评估：

- **可逆性**：变更是否可以通过回滚、恢复或重新部署安全撤销。
- **数据敏感性**：是否涉及真实用户数据、个人信息、支付数据、生产凭据或其他敏感数据。
- **外部影响**：是否影响外部用户、生产环境、外部系统、资金或组织承诺。
- **影响与恢复成本**：失败后的影响范围、业务损失、合规后果和恢复难度。

任一维度达到高风险时，整体按高风险处理；无法判断时，先按更高风险处理，完成澄清后再降级。

### 15.2 风险等级与控制映射

| 风险等级 | 典型判断 | 测试要求 | 审批要求 | 回滚要求 | 人工验收 | 证据要求 |
| --- | --- | --- | --- | --- | --- | --- |
| 低 | 可逆；不涉及真实/敏感数据；只影响本地或内部小范围；容易恢复 | 核心路径、异常冒烟和必要的自动验证 | 按任务授权执行 | 保留 Git 回退或重新构建路径 | 任务级或里程碑抽查 | diff、可重跑命令、原始输出 |
| 中 | 部分可逆；涉及共享环境、测试数据或有限外部影响；恢复需要协调 | 独立测试和集成回归 | 合并、接口、数据和环境变更需要人工审查 | 明确回滚步骤，并在测试环境验证 | 任务级或集成级验收 | 独立复核、时间环境标记、分支和提交号 |
| 高 | 不可逆或难回滚；涉及真实/敏感数据、生产或外部系统；影响范围大或恢复成本高 | 独立复核，并增加适用的安全、隐私、性能和恢复验证 | 明确人工批准、变更窗口和发布门禁 | 备份、回滚或恢复方案必须先验证 | 里程碑级或发布级验收 | CI/可信执行记录、运行编号、commit SHA、构建产物地址、测试环境 ID、证据生成者和写入时间 |

## 十六、证据可信度与防伪造

### 16.1 问题

“提交证据”本身不能保证证据真实。Agent 可能编造测试报告、谎称验证通过、生成与实际情况不符的截图或日志。证据链的价值取决于可复核性，而不是数量。

### 16.2 复核机制

1. **独立复核**：关键验证由不同会话（测试会话或新建会话）重新执行，测试会话不信任开发会话的自测结论。
2. **原始输出留档**：保存命令的原始输出、退出码、执行时间和环境，而不是只写“测试通过”的摘要。
3. **可重跑命令**：每个验证给出可复现的命令；验收时人工或独立会话重新执行并对比结果。
4. **抽查**：人对关键证据（测试报告、截图、日志）抽查复核，尤其是高风险变更。
5. **时间与来源标记**：证据文件记录执行时间、环境标识、分支和提交号，防止张冠李戴。高风险场景还应记录 CI 或可信执行环境的运行编号、commit SHA、构建产物地址、测试环境 ID、证据生成者和写入时间；仅本地执行时标记为本地自报证据。
6. **关键产物哈希**（可选，高风险项目）：对发布产物或数据文件计算哈希，验收时比对，防止中间被篡改。

### 16.3 分级要求

| 风险等级 | 证据要求 |
| --- | --- |
| 低（个人项目） | 保留命令输出和 diff，验收时重跑关键冒烟用例 |
| 中（标准项目） | 测试会话独立复核关键路径，全部证据归档 |
| 高（强监管项目） | 关键验证独立复核 + CI/可信执行记录 + 时间戳 + 审批记录 + commit SHA/构建产物/测试环境关联 + 可选哈希比对 |

> 声称“验证通过”必须附带可重跑的命令和原始输出；无法复现的“通过”视为未验证。

## 十七、Token 成本与预算控制

### 17.1 成本来源

多会话、长项目的开销主要来自：

- 上下文长度：会话越长，每次请求携带的输入越多
- 重复分析：多个会话反复读取同一批大文件
- 交接成本：文档更新、任务契约、证据整理本身也消耗 Token
- 返工：依赖未识别、验收未通过导致的重复执行

### 17.2 估算与预算

- 任务级：每个任务在契约中预估规模（小/中/大），大型任务拆分为多个小任务执行
- 会话级：为每个会话设定上下文上限，接近上限时归档并新建会话（见 7.3）
- 项目级：设定周/月预算上限，超限时降级采用方案（完整版 → 标准版 → 轻量版）或暂停非关键任务

### 17.3 控制手段

1. **控制会话长度**：上下文过长时及时归档，重要状态写入 docs/ 和 tasks/，不在同一会话中硬撑。
2. **上下文瘦身**：AGENTS.md 保持精简，任务契约只携带必要字段，大文件只读取相关片段。
3. **避免重复分析**：总控汇总分析结果，避免每个会话重复读同一批大文件。
4. **并行分摊**：真正独立的任务并行执行，减少串行等待；并行前先确认环境无冲突（见第十二节）。
5. **记录实际消耗**：会话结束后记录实际 Token 消耗，用于校准后续估算。

### 17.4 注意

> 不能为了省 Token 而强行拆散高度耦合的任务（见 10.4）。省 Token 的正确方式是减少重复和缩短上下文，而不是制造更多交接。

## 十八、人工验收的可操作性

### 18.1 问题

“结果是否符合真正的业务意图”对非技术负责人过于抽象。验收需要可操作的清单、用例和结论表单。

### 18.2 验收清单模板

按任务类型准备清单：

```text
功能验收清单（每个用例一行）：
用例编号：CASE-001
前置条件：
操作步骤：
预期结果：
实际结果：
通过 / 失败：

界面验收清单：
页面/视图：______ 对照设计稿：是/否
交互点检查：______ 异常状态展示：是/否

数据验收清单：
核对项：______ 期望值：______ 实际值：______ 通过/失败：______

边界与异常验收清单：
输入/场景：______ 预期处理：______ 实际处理：______ 通过/失败：______
```

### 18.3 冒烟用例、演示脚本与结论表单

- 每次里程碑验收准备 5-10 条核心路径冒烟用例，验收人逐条执行。
- 提供演示脚本：按顺序引导验收人走一遍关键操作，每步标注预期结果。
- 验收结论表单：

```text
验收结论：通过 / 有条件通过 / 退回
剩余条件（有条件通过时必填）：
证据路径：
验收人：______ 日期：______
```

### 18.4 验收分级

| 级别 | 验收内容 | 适用 |
| --- | --- | --- |
| 任务级 | 冒烟用例 + 自动验证结果复核 | 标准版日常任务 |
| 集成级 | 冒烟用例 + 联调回归 + 数据核对 | 集成任务、联调之后 |
| 里程碑级 | 完整验收清单 + 演示脚本 + 已知风险确认 | 版本发布、交付节点 |

验收人只需按清单操作、对比预期、填写结论，不需要理解实现细节；退回时附上具体用例编号和失败现象，方便开发会话定位修复。

| AI Agent 对象 | 项目管理职责 |
| --- | --- |
| Project | 一个长期项目或代码库的容器 |
| Chat | 一个独立结果或目标 |
| Goal | 一项连续的多步骤工作 |
| Worktree | 一个并行代码修改空间 |
| `AGENTS.md` | 项目级规则、边界、命令和验收约束 |
| Git | 变更、分支、回滚和集成依据 |
| `docs/` | 状态、架构和决策的持久化事实源 |
| `tasks/` | 任务契约、依赖和状态 |
| `tests/` | 测试代码和测试用例 |
| `evidence/` | 可复核的执行、测试、审查和验收证据 |

公开文档和相关工程实践提供了可复用原则：长期工作放在项目中；不同结果使用不同会话；连续多步骤任务保持在同一会话；独立代码任务使用 Worktree 并行；多个会话不要同时修改同一批文件；持久规则和背景写入 `AGENTS.md` 或项目文档。这些原则不是适用于所有 AI Agent 的单一官方最佳范式，具体能力和落地方式取决于平台、代码托管和权限环境。

## 二十一、分层采用：轻量版 / 标准版 / 完整版

### 21.1 为什么分层

完整流程（全部角色会话、集成任务、全套证据）对个人项目和小任务过重，仪式成本可能超过拆分收益。实际采用时应按项目特征选择起点，随复杂度上升而升级，而不是一步到位。

### 21.2 三档定义

**轻量版（个人项目、原型、单会话可完成的任务）**

- 单会话完成规划 → 编码 → 自测 → 自查
- 事实源仅保留 `AGENTS.md` + `docs/status.md`
- 证据从简：Git diff + 测试命令输出
- 人工验收只在里程碑或提交前进行
- 适用：探索原型、内部工具、明确的小功能

**标准版（小团队、中低风险、模块化项目）**

- 总控 + 开发/UI + 测试 + 审查，按目标分会话
- 任务契约 + 依赖表 + Worktree 并行 + 环境分配
- 任务级自动验证，集成级和里程碑级人工验收
- 适用：大多数 Web/App 项目、前后端分离的中型项目

**完整版（多模块平台、中高风险、多人协作、强监管）**

- 本文全部机制：全部角色会话、集成任务、证据链与防伪造、权限落地配置、Token 成本控制
- 适用：支付/医疗/金融、生产部署、多团队协作项目

### 21.3 升级与降级信号

| 出现以下信号 | 应升级到 |
| --- | --- |
| 多个目标频繁修改同一批文件 | 标准版（依赖管理 + 集成任务） |
| 涉及真实数据、外部发送或生产部署 | 完整版（权限落地 + 人工门禁） |
| 并行会话出现运行环境冲突 | 标准版/完整版（环境分配表） |
| 需求高度不确定（探索性） | 不升级，回到“假设 → 实验 → 结果 → 决策”循环 |

| 预算或复杂度下降 | 应降级到 |
| --- | --- |
| 单任务可独立完成、无并行 | 轻量版 |
| 项目进入维护期、变更很小 | 轻量版或标准版 |

### 21.4 选择建议

> 从轻量版起步，出现耦合、并行、真实数据或合规要求时再升级；升级不是推翻已有工作，而是在现有事实源和证据之上增加控制层。

## 二十二、最终总结

这套方法最值得保留的不是“把所有角色放进不同对话”，而是建立一条可追踪的执行链：

> 一个项目维护一个事实源；一个目标形成一个责任清晰的会话；目标之间的依赖通过契约、依赖表和集成任务管理；并行代码使用 Worktree 隔离；测试验证真实结果；审查只发现问题；总控汇总目标和证据；重要操作和最终验收由人决定。

一句话版本：

> 总控负责目标与证据，执行会话负责产物，测试负责真实验证，集成任务负责处理耦合，验收由人做最终决定。

采用建议：

> 从轻量版起步，随耦合、并行、风险和合规要求升级；证据必须可复核，权限必须能落地，成本必须可控制。
