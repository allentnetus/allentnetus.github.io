知识库最常见的误区，是把“收集到资料”误认为“沉淀了知识”，再把“AI 已经整理过”误认为“结论已经可靠”。结果往往是原始出处找不到、判断过程无法复盘、自动化输入和正式成果混在一起。

要解决的不是文件夹不够多，而是资料在不同阶段应承担什么角色。这篇文章从理论、实践和操作三个层面，介绍一套由 AI Agent 协作、但关键判断仍由人掌握的知识库工作流。

为避免暴露具体项目和本地环境，以下所有项目名称、路径与示例均使用统一的匿名占位：根目录为 `D:\ABC-Vault`，示例项目为 `Project-ABC`。

## 第一部分：理论——让知识库成为可解释的工作流

### 1. 资料有状态，处理动作也应有边界

一份资料从进入系统到成为可复用知识，至少经历四种状态：

| 状态 | 含义 | 此时可以做什么 | 此时不应做什么 |
| --- | --- | --- | --- |
| 待处理 | 原件刚进入收件箱 | 保留原件、来源、时间 | 自动分析、外发、删除 |
| 已入库 | 已补元数据并找到长期位置 | 检索、关联、作为项目输入 | 把二手资料写成确定事实 |
| 已形成输出 | 用户明确要求后形成的报告或方案 | 评审、交付、持续维护 | 与自动化输入混为一谈 |
| 已验证复用 | 经反馈验证、可跨项目使用的经验 | 提炼为知识或工作流 | 脱离证据无限泛化 |

用一句话概括：**进入知识库只是接收，经过验证和明确授权后，才可能成为分析或输出。**

### 2. 四段式流程：接收、入库、分析、反馈

一条完整的资料链路可以这样表示：

```text
外部资料 / 临时想法
  → 00_Inbox（接收）
  → Inputs / Knowledge（验证后入库）
  → Process / Outputs（明确要求后分析与交付）
  → Feedback（验证、复盘与下一轮改进）
```

这四段不能随意合并：

- **接收**解决“资料别丢”；
- **入库**解决“原件、来源和归属可追溯”；
- **分析**解决“基于哪些证据形成了判断”；
- **反馈**解决“判断后来是否成立，以及经验能否复用”。

当 AI Agent 参与其中时，最适合承担的是清点、格式检查、元数据补充、候选路由、日志和待确认项生成；它不应替用户擅自把输入升级为结论，更不应越过授权去发布、外发或删除资料。

### 3. 三条决定系统质量的原则

**原件优先。** 可直接阅读的网页、Markdown、会议记录和附件要保留原文。摘要、链接笔记和 AI 概述帮助导航，但不能替代证据；PDF 的文字层或 OCR 结果也只是检索伴生材料，关键数字与表格仍要能回看原页。

**专题优先。** 资料的长期价值常来自作者、机构或系列上下文，而不是标题关键词。路由时优先级应是：已有来源专题 > 用户明确用途 > 通用内容类型。

**人工确认优先。** 资料归属不明、事实待核验、是否形成正式输出、是否对外发送、是否提交远程仓库等动作，必须由人确认。自动化的目标是减少重复劳动，不是把责任也自动化。

## 第二部分：实践——以 Project-ABC 为例搭建系统

下面用一个匿名项目 `Project-ABC` 演示如何把上述原则落成目录、规则和一次完整处理过程。

### 1. 目录结构：先区分全局入口与项目工作台

```text
D:\ABC-Vault
├── 00_Inbox/                         # 所有未处理资料的统一入口
│   ├── manual/                        # 手动想法、摘录、临时材料
│   ├── web/                           # 网页文章与公开链接
│   ├── pdf/                           # PDF、扫描件和附件
│   ├── im/                            # 即时消息或协作平台资料
│   └── automation/                    # 自动化收集到的输入
├── 10_Projects/
│   └── Project-ABC/
│       ├── Inputs/                    # 已确认归属的原始证据
│       ├── Process/                   # 分析框架、讨论、方案与决策记录
│       ├── Outputs/                   # 明确要求后形成的阶段成果
│       ├── Feedback/                  # 评审、验证和复盘记录
│       └── skills/                    # 仅适用于 Project-ABC 的工作流
├── 20_Knowledge/                      # 可跨项目复用的知识
├── 30_MOC/                            # 主题地图与导航
├── 50_Skills/                         # 全库通用工作流
├── 60_Templates/                      # 模板
├── 70_Automation/
│   └── logs/                          # 运行与处理日志
├── 80_Outputs/                        # 跨项目或对外的正式成果
└── 90_Archive/                        # 已处理、拒收或失活材料
```

这里的关键不是目录数量，而是每个目录的责任边界：`00_Inbox` 只接收，`Project-ABC/Inputs` 保存证据，`Process` 保存判断过程，`Outputs` 保存交付结果，`Feedback` 保存结果回流。

### 2. 一条资料怎样进入 Project-ABC

假设用户发现一篇与 `Project-ABC` 直接相关的外部文章，暂时还不确定是否值得形成报告。

第一步，先把文章原文或链接保存到：

```text
D:\ABC-Vault\00_Inbox\web\2026-08-06_ABC主题观察.md
```

文件可以先保持很简单：

```md
# ABC主题观察

来源链接：https://example.com/abc
保存原因：可能与 Project-ABC 的当前研究有关，待整理后确认。
```

第二步，用户明确触发入库整理。AI Agent 先清点范围、读取原件、检索 `Project-ABC` 的既有专题，再补充元数据。例如，整理后的原件可以进入：

```text
D:\ABC-Vault\10_Projects\Project-ABC\Inputs\ABC主题\2026-08-06_ABC主题观察.md
```

相应的 YAML 不追求复杂，但至少让来源和用途可追溯：

```yaml
---
title: "ABC主题观察"
type: "source"
status: "active"
source: "web"
source_url: "https://example.com/abc"
project: "Project-ABC"
topic:
  - "ABC主题"
confidence: "to_verify"
created: "2026-08-06"
updated: "2026-08-06"
tags:
  - source
  - project-abc
---
```

第三步，AI Agent 把本次处理写入日志，而不是只告诉用户“已整理”。例如：

```text
D:\ABC-Vault\70_Automation\logs\2026-08-06.md
```

日志应至少说明：处理了哪份原件、从哪里来、为什么进入 `Project-ABC/Inputs`、是否有待核验事项。这样，未来看到一份资料时，能够回溯它的来源和路由理由。

### 3. 从 Inputs 到 Outputs：必须显式跨越的一步

文章进入 `Project-ABC/Inputs` 后，只意味着它已成为项目可用证据，并不意味着已经被分析。

只有用户明确提出类似“基于 Project-ABC 的 Inputs 形成方案”这样的请求时，AI Agent 才应进入分析阶段：

```text
Project-ABC/Inputs/ABC主题/
  → Project-ABC/Process/2026-08-06_ABC主题分析框架.md
  → Project-ABC/Outputs/2026-08-06_ABC主题阶段方案.md
```

`Process` 用来保存证据筛选、备选方案、风险和取舍；`Outputs` 则只放可供评审或交付的版本。这样既能避免把半成品当结论，也能在反馈出现后知道应修改判断过程还是最终表达。

### 4. 反馈如何让系统越来越有用

当 `Project-ABC` 的方案被评审、落地或否决后，结果写入：

```text
D:\ABC-Vault\10_Projects\Project-ABC\Feedback\2026-08-20_ABC主题复盘.md
```

如果多次复盘后发现某个检查清单或判断框架能服务于多个项目，再将它提炼到：

```text
D:\ABC-Vault\20_Knowledge\ABC方法论.md
```

如果它已经成为稳定、重复的操作，再升级为全库工作流：

```text
D:\ABC-Vault\50_Skills\ABC整理与核验.skill.md
```

这就是“从收件箱到知识资产”的完整含义：资料不是通过复制进入知识区，而是通过证据、判断和反馈逐步获得复用价值。

## 第三部分：操作手册——如何日常使用这套系统

### 1. 日常只需要记住三件事

```text
1. 不确定放哪里，先放 D:\ABC-Vault\00_Inbox\manual\。
2. 放进收件箱不等于已经整理，需明确让 AI Agent 处理。
3. 整理只做入库；要分析或生成方案，必须再次明确提出。
```

### 2. 各类资料放在哪里

| 资料类型 | 放置位置 | 最低要求 |
| --- | --- | --- |
| 临时想法、会议随手记 | `00_Inbox/manual/` | 保留原文即可 |
| 网页文章、公开链接 | `00_Inbox/web/` | 写下链接与保存原因 |
| PDF、扫描件、附件 | `00_Inbox/pdf/` | 保留原 PDF，不覆盖原件 |
| 协作平台消息 | `00_Inbox/im/` | 保留发送人、时间与原链接 |
| 自动化推送资料 | `00_Inbox/automation/` | 保留生成时间与来源说明 |

仍以第二部分的例子为准：与 `Project-ABC` 相关的网页文章先放入 `D:\ABC-Vault\00_Inbox\web\`，整理后才进入 `D:\ABC-Vault\10_Projects\Project-ABC\Inputs\`。

### 3. 可以直接对 AI Agent 说的话

**整理一批网页资料：**

```text
请整理 D:\ABC-Vault\00_Inbox\web 下的新资料。
只做原件保留、YAML、专题优先路由、日志和待确认事项；不要生成报告或发布内容。
```

**只处理 Project-ABC 相关资料：**

```text
请检查 D:\ABC-Vault\00_Inbox\web 中与 Project-ABC 有关的资料，
确认后放入 Project-ABC 的 Inputs，并列出无法判断归属的条目。
```

**从输入形成阶段成果：**

```text
请基于 D:\ABC-Vault\10_Projects\Project-ABC\Inputs\ABC主题\
形成分析框架和阶段方案：过程稿放入 Process，交付稿放入 Outputs，
并明确列出证据不足与待验证事项。
```

**查看还有哪些没有处理：**

```text
请清点 D:\ABC-Vault\00_Inbox 下仍未处理的资料，按来源列出数量、异常和建议的下一步。
```

### 4. 哪些动作需要用户确认

AI Agent 可以协助判断，但以下动作应由用户明确授权：

- 不确定资料是否应进入 `Project-ABC`；
- 将二手摘要、自动化内容或外部观点写成确定事实；
- 从 Inputs 生成正式 Outputs；
- 删除、覆盖、批量移动或重命名资料；
- 发送邮件、即时消息或发布博客；
- 提交或推送到远程代码仓库；
- 处理任何涉及交易、资金、账号或敏感信息的动作。

### 5. 出现问题时的最小排查顺序

如果不知道资料应该去哪：先放 `D:\ABC-Vault\00_Inbox\manual\`。

如果自动化推送后找不到资料：依次检查 `00_Inbox/automation/`、当天处理日志和原始来源是否成功送达。

如果 AI Agent 整理后仍有不确定项：优先确认三件事——资料归属、是否需要查一手来源、是否可以进入正式输出。不要为了清空待确认清单而跳过判断。

## 结语：自动化服务于判断，而不是替代判断

AI Agent 能让资料接收、整理、格式化和记录变得更快，但一套知识库真正的价值仍来自可解释性：原件是否还在、来源是否可查、分析是否基于足够证据、结论是否经过授权、反馈能否回流到下一轮实践。

当 `D:\ABC-Vault` 中的每条资料都能沿着“收件箱 → 入库 → Project-ABC 的输入与输出 → 反馈与复用”的路径被理解时，知识库才不只是存放文件的地方，而会成为持续积累和协作决策的基础设施。
